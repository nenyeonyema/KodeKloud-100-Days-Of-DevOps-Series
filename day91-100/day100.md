# Task 100 — EC2 Instance and CloudWatch CPU Alarm with Terraform

## Overview

> The Nautilus DevOps team has been tasked with setting up an EC2 instance for their application. To ensure the application performs optimally, they also need to create a CloudWatch alarm to monitor the instance's CPU utilization. The alarm should trigger if the CPU utilization exceeds 90% for one consecutive 5-minute period. To send notifications, use the SNS topic named xfusion-sns-topic, which is already created.
> Launch EC2 Instance: Create an EC2 instance named xfusion-ec2 using any appropriate Ubuntu AMI (you can use AMI ami-0c02fb55956c7d316).
> Create CloudWatch Alarm: Create a CloudWatch alarm named xfusion-alarm with the following specifications:
> Statistic: Average
> Metric: CPU Utilization
> Threshold: >= 90% for 1 consecutive 5-minute period
> Alarm Actions: Send a notification to the xfusion-sns-topic SNS topic.
> Update the main.tf file (do not create a separate .tf file) to create a EC2 Instance and CloudWatch Alarm.
> Create an outputs.tf file to output the following values:
> KKE_instance_name for the EC2 instance name.
> KKE_alarm_name for the CloudWatch alarm name.
Notes:
> The Terraform working directory is /home/bob/terraform.
> Right-click under the EXPLORER section in VS Code and select Open in Integrated Terminal to launch the terminal.
> Before submitting the task, ensure that terraform plan returns No changes. Your infrastructure matches the configuration.

## `main.tf`

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

# EC2 Instance
resource "aws_instance" "xfusion_ec2" {
  ami           = "ami-0c02fb55956c7d316"
  instance_type = "t2.micro"

  tags = {
    Name = "xfusion-ec2"
  }
}

# Look up the existing SNS topic ARN by name
data "aws_sns_topic" "xfusion_sns" {
  name = "xfusion-sns-topic"
}

# CloudWatch Alarm — CPU utilisation >= 90% for 1 x 5-minute period
resource "aws_cloudwatch_metric_alarm" "xfusion_alarm" {
  alarm_name          = "xfusion-alarm"
  comparison_operator = "GreaterThanOrEqualToThreshold"
  evaluation_periods  = 1
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  period              = 300
  statistic           = "Average"
  threshold           = 90

  dimensions = {
    InstanceId = aws_instance.xfusion_ec2.id
  }

  alarm_description = "Alarm when CPU utilization exceeds 90% for one 5-minute period"
  alarm_actions     = [data.aws_sns_topic.xfusion_sns.arn]
}
```

## Configuration Breakdown

### `aws_instance` — EC2 Instance

```hcl
resource "aws_instance" "xfusion_ec2" {
  ami           = "ami-0c02fb55956c7d316"
  instance_type = "t2.micro"

  tags = {
    Name = "xfusion-ec2"
  }
}
```

The AMI `ami-0c02fb55956c7d316` is Ubuntu 22.04 LTS in `us-east-1`. The `Name` tag sets the display name in the AWS console.

### `data "aws_sns_topic"` — Look Up Existing SNS Topic

```hcl
data "aws_sns_topic" "xfusion_sns" {
  name = "xfusion-sns-topic"
}
```

The SNS topic already exists — it must not be recreated by Terraform. A **data source** reads existing AWS infrastructure without managing its lifecycle. The data source exposes the topic's ARN as `data.aws_sns_topic.xfusion_sns.arn`, which is referenced in the alarm's `alarm_actions`.

> If `aws_sns_topic` were used as a `resource` instead of `data`, Terraform would try to create a new topic — and fail if one with that name already exists, or silently create a duplicate.

### `aws_cloudwatch_metric_alarm` — CloudWatch Alarm

```hcl
resource "aws_cloudwatch_metric_alarm" "xfusion_alarm" {
  alarm_name          = "xfusion-alarm"
  comparison_operator = "GreaterThanOrEqualToThreshold"
  evaluation_periods  = 1
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  period              = 300
  statistic           = "Average"
  threshold           = 90

  dimensions = {
    InstanceId = aws_instance.xfusion_ec2.id
  }

  alarm_description = "Alarm when CPU utilization exceeds 90% for one 5-minute period"
  alarm_actions     = [data.aws_sns_topic.xfusion_sns.arn]
}
```

**Every argument mapped to the task spec:**

| Argument | Value | Task Requirement |
|----------|-------|-----------------|
| `alarm_name` | `"xfusion-alarm"` | CloudWatch alarm name |
| `comparison_operator` | `"GreaterThanOrEqualToThreshold"` | Threshold: **>=** 90% |
| `evaluation_periods` | `1` | **1** consecutive period |
| `metric_name` | `"CPUUtilization"` | Metric: **CPU Utilization** |
| `namespace` | `"AWS/EC2"` | EC2 metric namespace |
| `period` | `300` | **5 minutes** (300 seconds) |
| `statistic` | `"Average"` | Statistic: **Average** |
| `threshold` | `90` | Threshold: **90%** |
| `dimensions.InstanceId` | EC2 instance ID | Scoped to the specific instance |
| `alarm_actions` | SNS topic ARN | Notify `xfusion-sns-topic` |

**`period` in seconds:** CloudWatch periods are always expressed in seconds. 5 minutes = 300 seconds. Valid CloudWatch period values must be multiples of 60.

**`evaluation_periods = 1`:** The alarm triggers after 1 consecutive period breaching the threshold. With `period = 300`, this means CPU must exceed 90% for at least one uninterrupted 5-minute window.

**`dimensions`:** Scopes the metric to the specific EC2 instance. Without a dimension, the alarm would evaluate the metric across all EC2 instances in the account.

```bash
# View Terraform outputs
terraform output

aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=xfusion-ec2" \
  --region us-east-1 \
  --query "Reservations[*].Instances[*].{ID:InstanceId,Type:InstanceType,State:State.Name}" \

  --alarm-names xfusion-alarm \
  --region us-east-1 \
  --query "MetricAlarms[*].{Name:AlarmName,Metric:MetricName,Threshold:Threshold,Period:Period,Periods:EvaluationPeriods,Stat:Statistic,State:StateValue}" \
  --output table

aws cloudwatch describe-alarms \
  --alarm-names xfusion-alarm \
  --region us-east-1 \
  --query "MetricAlarms[*].AlarmActions" \
  --output json
```

## CloudWatch Alarm States

After creation, the alarm cycles through these states:

| State | Meaning |
|-------|---------|
| `INSUFFICIENT_DATA` | Not enough metric data yet (initial state) |
| `OK` | CPU is below 90% |
| `ALARM` | CPU has been ≥ 90% for 1 consecutive 5-minute period → SNS notification sent |

The alarm starts in `INSUFFICIENT_DATA` until CloudWatch receives the first 5-minute data point from the instance.
